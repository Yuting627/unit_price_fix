Item Inspection is a quality control process used to detect and correct unusual sales and price data at 
the item level in scanned retail data. It automatically reviews weekly store data to identify outliers — 
unusually high or low values that may be due to errors or inconsistencies.
Here's how it works:
 It checks for extreme values in sales rates and prices, comparing each item across multiple 
stores in a given period.
 The system uses statistical methods (like the Fuller algorithm) to flag and optionally correct 
these outliers.
 Recent improvements make this process more accurate by:
 Repeating the correction loop to ensure consistency when multiple issues are found.
 Applying the same correction to identical prices to avoid illogical differences in the output.
 Dynamically updating input data after each correction to improve the next round of checks.
This ensures that the final data used for reporting or analysis is reliable, avoiding distortions that can 
result from raw errors or anomalies in the original retailer data.\n\n===== PAGE 6 =====\nConnect Data Science – Item Inspection (Draft)

1.1 1.   Project Summary / Scope of the project
1.1.1 1.1. Problem Opportunity Statement
Current version of II relies on two consecutive rates in order to determine whether correction is needed 
or not. Inconsistent corrections are observed in cases when there is small difference between two 
observations after the first identified for correction. In the same time when it comes to prices, equal 
prices as input are corrected and output as different, which is not desired behavior for US team.
1.1.2 1.2. Project Scope
The request was to analyze the current Item Inspection methodology and to determine how to get an 
enhancement in the procedure which will ensure consistent detection and correction on all 
observations following the first identified as outlier.
NB! Out of scope:
-        Currently number of observations for detection and correction is dependent on tail size only 
regardless of where in the set of observations the break appears
1.1.3 1.3. Outcome of Methods Work
As part of the request the following topics were reviewed:
-        The statistical methodology and operational process of Item Inspection algorithm for High Sales 
Rates; both High and Low Price Rates
-        Simulated extreme cases examples that replicate the issue at hand
-        Root Cause of the inconsistency for detection, based on moving difference between rates 
differences
The following enhancement is suggested to address the identified root cause: iterative run of the 
process with dynamic update on the input values with the corrected ones, with constant correction for 
same input Price Rates.
1. Price Rates both left and right
                                                    i.     Same corrected rate if same initial price
                                                   ii.     No gaps in corrections (dynamic update of the tail)
2. Sales Rates
                                                    i.     No gaps in corrections (dynamic update of the tail)\n\n===== PAGE 7 =====\nConnect Data Science – Item Inspection (Draft)

 CorrectRelseExtraProm – this parameter is used during the assessment of the significance 
of proposed corrections on both sales units and prices, and the decision on whether to 
apply or not these corrections. Its purpose is to increase further the marginal value against 
which the effect of the proposed correction is compared; i.e., in the case of promotional 
activities, it is natural to see larger sales, and we do not want to correct those, so we raise 
the limit. Suppose any promo activity is observed in the data (as part of item inspection). In 
that case, the weighted promo distribution is computed, and the proposed correction is 
compared to a marginal value, which is additionally multiplied by the value of this 
parameter. In the presence of promo activity, the bigger the value of this parameter, the 
bigger the chance to ignore the correction, and vice versa. In the absence of promo activity, 
this parameter is set to 1, and the marginal value, on which it is decided whether to apply a 
correction, is not further boosted.
 FullerCorrectLimit – this parameter has direct effect on the size of the correction proposed 
for each detected outlier. It is a probability and has the same effect on the proposed 
correction when set to p or 1-p, where p is a number between 0 and 1. For example we 
would obtain the same result if item inspection were run with this parameter set to 0.1 and 
0.9; 0.2 and 0.8, 0.3 and 0.7, 0.4 and 0.6. When the value of this parameter is a number 
above 0.5, the larger it is, the larger the proposed correction is, and vice versa. Respectively, 
when the value of this parameter is less than 0.5, the lower it is, the bigger the proposed 
correction is. The chart below illustrates how the proposed correction changes when 
changing the value of this parameter.

1.3 3.   Dynamic Sales Rates update
The enhancement is affecting the first stage of II process (Fuller: Inspection/Correction engine) by 
adding iterative element for the engine run. The process is run as many times as many observations 
where calculated to be inspected. If correction is proposed for the first observation from the list, in the 
second run the corrected value will be placed as input value. And so on and so forth.

rates

is accounting for equal input prices. In case of two or more consecutive observations with the same 
input price value – the same correction is applied to the following one or more observations, thus

Item inspection in SirVal bypasses UPCs that have five stores or fewer selling in a given week and IBD.

The proposal relies on a cross-sectional type of validation given the nature of price behavior. This is an

 Filter v_prices (prices > min_price, default = 0)

 t_perc_ul = q_high quantile (v_prices)
