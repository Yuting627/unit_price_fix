\n===== SLIDE 1 =====\nWhy we need FOVA (Formal Validation) processes \nDEFINITION\nWhat the process does\nFOVA is first validation process in SIRVAL process flow.
FOVA perform store level validation where the focus is on the general acceptance of the store rather than problems in a limited set of items.\nFor each store, current week’s data will be compared with Last Good period’s data (not salvaged / estimated / Xcopied)
The comparison is done at different levels like Total sale, Units, Price, Cref (Barcode), Supergroup etc…
Various statistical tests is run by the system during this comparison using pre-calculated acceptance range.+
Detailed Report of comparison is generated as the output of the process.
User can manually validate report for those stores which fail these statistical test/s and decide on whether to accept the data or not.
If data of the store is received / loaded for the first time, system automatically considers it to be a DATA_GOOD store.\n\n===== SLIDE 2 =====\nFOVA Handling – Starters training\nLast update on  10-07-2023

Only those stores which are able to pass majority of statistical test and whose trend falls within the trend are suggested as DATA GOOD by the system.

User is not supposed to check FOVA Report for DATA GOOD tagged stores as per SOP however as per country guidelines, if it is required to be checked user need to do so.

DATA_GOOD - NO REASONS FOR ESTIMATION - PENDING RELAUNCH :

This tag is assigned to those stores for which minimum number of stores loaded for respective FBD is yet to be achieved.

For such cases, system performs limited statistical test on such stores and pass the judgement as Data Good with this tag if those tests are passed.

However system keeps it noted to re-launch and run FOVA process again once Minimum store loaded count of the FBD is reached.

This tag indicates the possibility of some missing data in Current Period compared to LGP. Reasons for the missing items can be complete data (for all items) is not received

\n\n===== SLIDE 22 =====\nHOW THE PROCESS WORKS\nFOVA Tags\nIDENTICAL VOLUMETRICS-ESTIMATION PROPOSED :

This tag means data of LGP and CP are exactly same.
In the real world scenario this cannot be true that we have same volume, units and value as we had in previous week.
This is possible only when data is copied over from last period.
The operator needs to apply salvation or need to highlight to Onshore.
An operator can identify problem from all the tables starting from Global freq.

 
STRONG UPWARD TREND :

This tag means shop has upward data compared to previous period. It may be due to festival or seasonality impact in prevailing country / region.
Trend of all the shops across the retailer must be checked. If majority of the shops are having same trend, such store can be set as Ok. 
If without any festival or season or any specific reason, such scenario persists then the operator needs to highlight to onshore / retailer and if required, apply salvation process on such stores.
The operator can identify from Unit freq., Unit change freq., Price change freq., Supergroup tables.\n\n===== SLIDE 23 =====\nHOW THE PROCESS WORKS\nFOVA Tags\nNO RESET - ESTIMATION PROPOSED :

When in data collection, dates are not reset correctly, No Reset tag is attached
In such cases, the data received is much higher or almost double then LGP.
The retailer may send the data for two weeks in one week itself. Since it is not expected, so if in 1 week turnover of the shop increases to double as compared to past weeks, it should be highlighted to onshore.
An operator can identify problem in Unit freq., Supergroup tables
An operator can observe double or more than double data in every Supergroup.\nSTRONG DOWNWARD TREND :

This tag is set when the shop has downward data in current week as compared to previous week. There may be a chance of festival or seasonality impact in prevailing country / region.
The operator should check trend of all the shops across the retailer. If major of the shops having same trend we can set such store as Ok. 
If without any festival or season or any specific reason, such scenario persists than there is some problem. The operator needs to highlight to onshore and if required, apply salvation process on such stores.
The operator can identify problem from Unit freq., Unit change freq., Price change freq., Supergroup tables
\n\n===== SLIDE 24 =====\nHOW THE PROCESS WORKS\nFOVA Tags\nIDENTICAL PRICE :
When most of the items are having the same price as of LGP’s price, then this tag will be affixed to FOVA report.
This may be normal for the cases, where prices are not changed frequently (e.g. Pharmacy shop). For such cases the operator can accept the data. 
When almost 90% items have same price in CP as in LGP.
The operator can identify problem in Unit freq., Cref freq. and Price change freq. tables.\nCHANGED PRICE :

When the price for most of the items are changed as compared to LGP’s price, then this tag will be affixed to FOVA report.
The change in price can be very high or very low or when there are changes in price in CP for almost 80% to 90% items as compared to LGP. The price may be changed due to promotional offers by the retailer.
The operator can highlight it to onshore when the price is changed for the stores without the promotional offers. For other specific reasons, salvation processes can be applied on such stores.
An operator can identify problem at Price freq. and Price change freq. table.\n\n===== SLIDE 25 =====\nHOW THE PROCESS WORKS\nFOVA Tags\nPrice Sync :

According to normal market conditions, when price increases, units sold should decrease and when the price decreases, units sold should increase.
FOVA reports will fall under this tag, when the price and units are not in synchronization as per the normal market conditions, i.e., when increase in price results in increase in units sold and when decrease in price results in decrease in units sold.
Apart from Price Sync table, the operator needs to refer other tables as well to take the FOVA decision.
An operator can see problem in Unit freq., Price freq., Unit change freq. and Price sync freq. table.\n\n===== SLIDE 26 =====\nHOW THE PROCESS WORKS\nFOVA Tags\nExceptional Positive OR Negative Trend :

This tag is set when the trend variant (calculated using previous and current period information) is violated the boundaries of trend lower/upper bound.
An acceptable range will be parameter driven which is calculated automatically by FOVA process using current and back 13 weeks.
If value do trend Variant is lower than Lower Bound (LB) then test will be tagged as “EXCEPTIONAL NEGATIVE TREND BEHAVIOUR” and If current period is higher than Upper Bound (UB) then it will be tagged as “ EXCEPTIONAL POSITIVE TREND BEHAVIOUR”.
Decision can be made as per the rules mentioned in the SOP.\nMissing Days :

This tag will be applicable for the store where daily sales information is received in the input (i.e. SIRPAIR files).
For such cases in FOVA report, Daily data table will be generated which will show day wise information.
If any expected day is missing, then store will be flagged as “MISSING DAYS”. Expected days need to be setup in the parameter values.
Decision can be made as per the rules mentioned in the SOP.\n\n===== SLIDE 27 =====\nHOW THE PROCESS WORKS\nFOVA Tags\nUNIDENTIFIED - NO LGW AVAILABLE :

\n\n===== SLIDE 32 =====\nDM 24442 - FOVA Price Change Enhancement:\nPreviously, the FOVA price check algorithm splits the price change compared to previous ‘good’ period into 3 brackets (‘less’, ‘equal’ and ‘more’) for detecting price issues. This validation works well in most cases. However, when an anomaly like sending price=1 for many or some of items in one or couple of days, can be ‘missed’ due to the fact that ‘less’ and ‘more’ do not measure the magnitude of change. 

A new algorithm is added in FOVA to detect price issues mentioned above. This new algorithm will enhance/replace the current ‘Changed Price’ fova tag detection. 

A new step is added in FOVA PARAMETER process to calculate the % of items for which the price has significantly changed for each week. This information will later be used by FOVA, to identify whether the current period data will be considered as price outlier or not. 

The new logic in FOVA PARAMETER process will be driven by the below new process parameters:  

PRICE_CHECK_ENABLE - Y/N - Whether to activate the calculation of price check parameters 
PRICE_CHECK_CALCULATE_WEEKS - Number of historical weeks to consider for price check parameter calculation 
PRICE_CHECK_CHANGE_LIMIT – The limit of absolute % price change vs preceding period, above which the price will be flagged as outlie

\nDec’22 CR\n\n===== SLIDE 33 =====\nDM 24442 - FOVA Price Change Enhancement:\nThe new process will require historical data to be used, and the number of weeks considered will be defined based on parameter PRICE_CHECK_CALCULATE_WEEKS.  


If the parameter PRICE_CHECK_ENABLE is activated, then FOVA PARAMETER will iterate over the periods in scope and will calculate for each shop: 

Number of items.
The number of items for which their price has changed more than X % based on previous period. X% will be based on the value of the parameter PRICE_CHECK_CHANGE_LIMIT.

Only common items (I.e., found on both period T and T-1) will be considered. 
The results will be stored in a new table named FOVA_PRICE_CHECK_LIMITS so they can be later used by FOVA process.  

\nDec’22 CR\n\n===== SLIDE 34 =====\nDM 24442 - FOVA Price Change Enhancement:\nThe FOVA process will also be enhanced to improve the price check logic.  
The new logic in FOVA process will be driven by the below new process parameters:  
PRICE_CHECK_ENABLE - Y/N - Whether t to activate the calculation of price check parameters 
PRICE_CHECK_BACK_WEEKS - Number - default 12 - Number of historical weeks to consider for price change limit calculation 
PRICE_CHECK_MIN_BACK_WEEKS – Number default 4 – Minimum number of historical weeks needed to use the price check algorithm 
PRICE_CHECK_CHANGE_LIMIT  - The limit of absolute % price change vs preceding period, above which the price will be flagged as outlier 

If the PRICE_CHECK_ENABLE parameter is activated, then the process will perform the below validations: 

The value of the parameter PRICE_CHECK_BACK_WEEKS must be >= PRICE_CHECK_MIN_BACK_WEEKS. If not, then write a message in the log and the new price check logic will be disabled 
\nDec’22 CR\n\n===== SLIDE 35 =====\nDM 24442 - FOVA Price Change Enhancement:\nAfter the existing price check logic is performed in FOVA, and if the PRICE_CHECK_ENABLE parameter is activated then a new procedure will be executed that will perform the below steps:  
Calculate for current period the percentage of items with price change over limit vs previous periods. 
Calculate from table FOVA_PRICE_CHECK_LIMITS based on historical weeks the price change limit to use for outlier check 
Flag the shop as price outlier based on above 
If eventually FOVA completes with a decision of FOVA OK (monitor tag 300) considering that the shop was flagged as price outlier with the new logic, then: 
The monitor tag will be overwritten to 361 
The monitor status will be modified to 1

Checking if Daily Data is Available for the store
If Daily Data are available, then a day is marked as missing if:
it has 0 sales 
and it was expected to receive data for that day (based on EXPECTED_DAYS parameter)

Defining the EXPECTED_DAYS parameter is not user friendly. In addition, the existing logic doesn’t consider any historical daily data as part of the decision making. Furthermore, in case we have missing daily data, then there is no system suggestion on how the data can be modified to arrive to valid situation. 

A new algorithm is added in FOVA process to enhance the daily data validation logic with a new algorithm. This algorithm is based on the store holiday calendar already available in SIRVAL, as well as historical daily data for the store. Based on these inputs, it identifies for which days we have missing daily data and suggest a factor that can be applied on the raw data to make the shop valid. 
  
A new logic is added in FOVA to enhance the current logic with a new algorithm if historical data is available for the store.

DAILY_DATA_FACTOR_SUGGESTION - Y/N - Whether to run the new algorithm to identify missing days in daily data and calculate an expansion factor
DAILY_DATA_FACTOR_HISTORY_WEEKS - Number - default 52 - Number of historical weeks to consider for daily data validation
DAILY_DATA_FACTOR_MIN_AVAILABLE_WEEKS – Number default 4 – Minimum number of historical weeks with correct daily data for the new logic to run (Data good)

The new process will require historical data to be used, and the number of weeks considered will be defined based on parameter DAILY_DATA_FACTOR_HISTORY_WEEKS. A validation will be added in the beginning of the FOVA process so that: 

If parameter DAILY_DATA = Y and

  \nDec’22 CR\n\n===== SLIDE 51 =====\nDM 25211 FOVA Missing Days Enhancement: \nIf we do have appropriate historical daily data available, then the system will proceed to perform the steps below based on new logic: 
  
Calculate the probability for the store to have sales on each day of the week using the historical daily data
Calculate the number of expected days for the week by summing up the probabilities of each day
Calculate the importance / share of each day in the week, based on the historical data
If number of expected days is equal to days received, then continue with the FOVA
If the number of days received is NOT equal to expected days, calculate the number of missing days
Based on number of missing days, iterate over the days for which we have not received data based on probability descending and perform the below actions:
Check against Holiday calendar (PUBLIC_HOLIDAYS table) if the missing day was holiday/special event. If the day is on calendar special/event, then consider that this day is not really missing 
If the missing day is not on holiday/special event, then flag the day as really missing

If eventually we have any days missing that cannot be justified based on holiday calendar, then a factor is calculated that should be applied in the raw data to expand it. The factor will be calculated based on the importance / share of the days identified as missing from the logic above.

Example:\nDec’22 CR\nHere, factor is calculated as below: 
Factor = 1+ (1- total shares of received data)/ total shares of received data 
            = 1+(1-0.728/0.728)             = 1.374\n\n===== SLIDE 52 =====\nDM 25211 FOVA Missing Days Enhancement: \nAs part of the above logic/mentioned steps, in case we have any days with missing daily data, and a factor has been calculated, then in all subsequent steps that FOVA is reading raw data, the SLOT1 and SLOT2 columns will be multiplied with this factor. This will allow the FOVA process to continue assuming that the daily data received did not have any gaps. 
  
If eventually FOVA completes with a decision of FOVA OK (monitor tag 300) considering that a daily data factor had been applied, then: 
The monitor tag will be overwritten to 358
The monitor status will be modified to include the value of the factor
  
This will allow the user to apply a correction to the store data to apply the factor and thus to arrive in a valid store situation for the period. \nDec’22 CR\n\n===== SLIDE 53 =====\nDM 25211 FOVA Missing Days Enhancement: \nBasic Process flow:\nDec’22 CR\n\n===== SLIDE 54 =====\nDM 26031 - FOVA Missing days Enhancement phase 2:\nFor Existing Fova missing days calculation on Daily data algorithm some adjustments are required.

In the existing process, part of FOVA, that identifies and flags Missing days on daily data there is a need to enhance the process so that under specific scenarios some additional days are flagged. The current process is flagging Missing Days in case # of days received is less than expected days.

Based on the new requirements if the probability value of a specific day is greater than a threshold (default 0.9) and no data has been received for the day, in case it is not defined as a holiday, it should then be flagged as a missing day even if the expected days criteria is met.

Below 2 criteria is considered for it:

Scenario 1: 

In case Days Received are more or equal to the expected days, but there are days with Probability > 0.9 not received and it is not a Holiday, then it should be considered and flagged as a missing day. 

Scenario 2:
In case Days Received are less than the expected days, but there are days with Probability > 0.9 not received and it is not a Holiday, then it should be considered and flagged as a missing day.

\n\n===== SLIDE 101 =====\nRules & Restriction - Daily Data\nWhat is a missing day?

A day when the data is  expected but not received in the input is called a missing day. Normal bank holiday or store closure days will not be considered as Missing days and they need to be communicated in advance.
These rules will be valid only for the retailers for which reliable daily sales information is received.

Census

If a day is missing for full retailer need to be captured from the retailer check.
If one/more day(s) is missing for one/few census store of a particular retailer, we accept the data, excluded  if we have received prior information is received for missing day (e.g. technical issue).

Sample

If a day is missing for full retailer need to be captured from the retailer check.
If one/more day(s) is missing for one/few sample store of a particular retailer, Data need to be factored/Estimated based on salvation rules.

Salvation Rule for missing day(s):-

If 2 or more days are missing then store must be Estimated.
If the weight of the day is higher than other days and miss a part of the assortment sold in a week then it must be estimated (fex Friday or Saturday for a hypermarket).
For all other missing day store need to be factor (the factor value must adjust the Rawdata to the expected level).
